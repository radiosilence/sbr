benchmarks

Measured on 2026-10-26. Both cores were given the same config file and run as clients of servers on loopback, so most of these figures are the cost of the client itself rather than of a network; one section measures a real server over a home connection.

Each figure is the lowest and highest of three rounds. The solid part of a bar reaches the lowest, the faint part the highest. The machines were loopback-only and some were shared with other builds, as noted under each chart, so a difference of a few percent is a tie. The raw tables and method are in BENCHMARKS.md.

proxy throughput, linux

OrbStack Linux VM with 8 vCPUs on an Apple M1 Pro, four streams for 5 s, three rounds. sing-box 1.14.4 release build (linux-arm64); the servers are sing-box.

sbr is ahead or level on every encrypted path: up to 18% on the TLS protocols, up to 57% on Shadowsocks-2022, 29–45% on hysteria2 upload at the same CPU per GB, and 41–50% on WireGuard upload at a fifth of the CPU per GB. Plain TCP relay to direct is the one row sing-box wins, by 20–47%: on Linux it moves bytes between two TCP sockets with splice(2) inside the kernel, while sbr copies them through userspace. Darwin has no splice, so on Apple platforms both copy.

through a real server

An M1 Pro on home Wi-Fi, each client a local SOCKS proxy to the same hysteria2 server (apernet hysteria, Hetzner, Salamander), downloading from a Hetzner speed-test file for 20 s, two rounds. With the tunnel off the same download ran at 472–500 Mbit/s.

sbr was 2–11% faster here at about 60% of sing-box's CPU. Both beat the direct download, because the server reaches the speed-test host by a better route than the home connection does. The server itself used roughly half a core while serving sbr at this rate.

vless + vision against xray, macos

Apple M1 Pro, Xray-core 26.10.21 with the reference deployment's configuration, Homebrew sing-box 1.14.4. Four streams for 5 s, three rounds back to back. The machine was in use during these runs, so compare the two clients within a row rather than with other charts.

On the padded path sbr is 5–20% faster and uses 15–49% less CPU per GB. With TLS inside the tunnel, where Vision copies directly, the two are level. The rows with TLS inside the tunnel vary widely between rounds for both clients.

The comparison uses Xray's TLS + Vision inbound because sing-box cannot connect to its REALITY inbound: sing-box removes X25519MLKEM768 from its REALITY ClientHello, which XTLS REALITY servers have refused since 2026-09-08. Over REALITY + Vision, sbr reached 8.9–9.3 Gbit/s up and 8.4–8.5 Gbit/s down in the same run.

hysteria2 against apernet hysteria, macos

Same machine and rounds, apernet hysteria 2.13.0 with Salamander.

Upload is 18–28% faster than sing-box at about 45% less CPU per GB; download is within 3–6% in throughput at 37% less CPU per GB. Two changes produced this. On Darwin, sbr sends and receives QUIC on a socket connected to the server, because macOS routes every unconnected sendto afresh and has no UDP GSO to amortise that cost; this halved upload CPU per GB. sbr also spreads streams over two QUIC connections, since one connection's packet processing runs on one core; on a phone this nearly doubled throughput.

wireguard, apple silicon

Apple M1 Pro, macOS, Homebrew sing-box 1.14.4 as the peer and as the comparison client, three rounds back to back. sbr runs on the single-thread runtime.

Upload is 5–21% faster than sing-box at 30% of its CPU per GB. Download is limited by the loopback sing-box server for both clients, and there sbr uses a third of sing-box's CPU per GB. Upload depends on connecting the UDP socket to its single peer: Darwin routes every unconnected sendto afresh, and connecting it more than doubled upload and halved its CPU per byte.

tun: kernel and userspace tcp stacks

OrbStack Linux VM with 8 vCPUs on an Apple M1 Pro, host shared with other builds (load average about 7); the two stacks ran back to back in each round. Four streams for 5 s from apps through the TUN, the engine and direct to a loopback server. CPU is whole-machine, including the kernel's own TCP work.

The kernel stack sends every segment through the kernel twice, from the app's socket to the TUN and from the TUN to sbr's listener; the userspace stack sends it once. The gap is widest at MTU 1280, where per-packet costs dominate. Both stacks are far faster than a phone's radio, so on a phone the CPU per byte is what matters. The app uses the userspace stack on iOS and tvOS. A real Darwin utun has not been measured yet.
