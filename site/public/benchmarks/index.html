benchmarks

Measured on 2026-10-25. Both cores were given the same config file and run as clients of servers on loopback, so these figures are the cost of the client itself rather than of a network.

Each figure is the lowest and highest of three rounds. The solid part of a bar reaches the lowest, the faint part the highest. The machines were loopback-only and some were shared with other builds, as noted under each chart, so a difference of a few percent is a tie. The raw tables and method are in BENCHMARKS.md.

proxy throughput, linux

Idle 4-vCPU Linux VM, four streams for 5 s. sing-box at HEAD (a6952cc), built with with_quic, with_utls, with_wireguard and with_gvisor; the servers are sing-box.

sbr is ahead on the encrypted paths. Plain TCP relay is level because sing-box uses splice(2) on Linux; Darwin has no splice, so on Apple platforms both cores copy. hysteria2 is level in throughput, with 8–15% less client CPU per GB for sbr. WireGuard upload is behind in this run, which predates the Darwin send-path change measured below.

vless + vision against xray, macos

Apple M1 Pro, Xray-core 26.10.21 with the reference deployment's configuration, Homebrew sing-box 1.14.4. Four streams for 5 s, three rounds back to back.

sbr uses 35–40% less CPU per GB on the padded path and is ahead or level in throughput on every row. The rows with TLS inside the tunnel vary widely between rounds for both clients.

The comparison uses Xray's TLS + Vision inbound because sing-box cannot connect to its REALITY inbound: sing-box removes X25519MLKEM768 from its REALITY ClientHello, which XTLS REALITY servers have refused since 2026-09-08. Over REALITY + Vision, sbr reached 20.0–20.6 Gbit/s up and 17.5–18.4 Gbit/s down.

hysteria2 against apernet hysteria, macos

Same machine and rounds, apernet hysteria 2.13.0 with Salamander.

sbr is behind here: upload reached 0.86–0.88 Gbit/s against sing-box's 1.25–1.32, at more CPU per GB. Download is level. On Linux against a sing-box server the two were level. macOS has no UDP GSO, so the cost of sending each datagram dominates; this path has not been profiled yet.

wireguard, apple silicon

Apple M1 Pro, macOS, Homebrew sing-box 1.14.4 as the peer and as the comparison client. The machine was shared with other builds (load average 10–17). sbr runs on the single-thread runtime that iOS uses.

Upload with four streams reached 1.54–2.16 Gbit/s for sbr and 1.23–1.80 for sing-box, and download is level, limited by the loopback server. The upload figures follow a change to connect the UDP socket to its single peer: Darwin routes every unconnected sendto afresh, and connecting it more than doubled upload and halved its CPU per byte.

tun: kernel and userspace tcp stacks

OrbStack Linux VM with 8 vCPUs on an Apple M1 Pro, host shared with other builds (load average about 7); the two stacks ran back to back in each round. Four streams for 5 s from apps through the TUN, the engine and direct to a loopback server. CPU is whole-machine, including the kernel's own TCP work.

The kernel stack sends every segment through the kernel twice, from the app's socket to the TUN and from the TUN to sbr's listener; the userspace stack sends it once. The gap is widest at MTU 1280, where per-packet costs dominate. Both stacks are far faster than a phone's radio, so on a phone the CPU per byte is what matters. The app uses the userspace stack on iOS and tvOS. A real Darwin utun has not been measured yet.
